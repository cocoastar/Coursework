# 轨迹冗余分析：从完整轨迹中识别重复、回退与停滞阶段

> 本周工作文档。目标：研究如何从完整 agent 轨迹里找出**重复尝试、反复回退、长时间无进展**的阶段，把【合理探索 / 必要验证 / 错误恢复】与【真正的低效重复】区分开，并结合成本（调用 / token / 耗时的可得代理）给出判断依据。重点攻克当前痛点——**误判"有意义但失败的尝试"**。

---

## 0. 数据与成本口径（先讲清局限）

分析基座：`RedundancyBench`（三域：airline / retail / telecom，轨迹源自 tau2-bench）。它本身就是"在完整轨迹里定位并分类冗余步"的标注集，与本周要求高度契合：

- **轨迹本体**：`final_traces.json → simulations[i].messages`，role 为 `user/assistant/tool`。assistant 的一个 `tool_calls` 元素与紧随其后的 `tool` 消息配成**一个"步"**（如 `[6,7]` = 调用 + 返回）。
- **标注**：`annotation.json` 每条给出 `redundant_step_idx`（成对下标）、`redundant_step_type`（四类）、`evidence_step_idx`（支撑证据）、`reason`（中文判断依据）、`confidence`。
- **四类冗余定义**（即本文要区分的核心）：

| 类型 | 判据 |
| --- | --- |
| Duplicated Step | 更早的有效步已提供该信息/操作，此步无新增。 |
| Abnormal Step | 一次外部/工具故障，被后续成功重试取代。 |
| Incorrect Step | 在当时的请求/政策/已知信息下，该动作不成立。 |
| Exploratory Step | 一次合理的搜索/诊断，但**事后看**未贡献必要信息。 |

**成本口径（重要局限）**：本数据集的 message **没有真实 token、没有时间戳、没有耗时**。因此成本一律用**代理指标**近似，耗时维度不可得：

| 成本维度 | 代理指标 | 说明 |
| --- | --- | --- |
| 调用成本 | `n_tool_calls` | 工具调用次数 |
| 上下文成本 | `tool_return_chars` → `≈token = 字符/4` | tool 返回内容体量，近似进入上下文的 token |
| 交互成本 | `n_turns` | 有文本的 user/assistant 回合 |
| **可节省成本** | `redundant_chars` | 冗余步占用的返回字符 = 若剔除可省下的代理 token |

脚本 `cost_proxy.py` 对全量轨迹计算上述指标。对高冗余的前 12 条轨迹统计：**冗余步占用了 61.4% 的 tool 返回 ≈token**——说明在这些轨迹里，"白做的工具交互"消耗了过半的上下文成本，识别冗余的收益显著。

## 1. 三类现象的识别信号

从完整轨迹里，用可计算的信号定位三类目标现象：

| 现象 | 轨迹上的信号 | 代理指标 |
| --- | --- | --- |
| **重复尝试** | 同名工具 + 相同/高度相似参数相邻多次出现 | `n_repeat_calls`（同名工具 `sum(count-1)`） |
| **反复回退** | `tool.error==true` 后紧跟同调用的重试；或"操作→检查→撤销→再操作"的往返 | `n_failed_calls` |
| **长时间无进展** | 连续多个工具调用均未改变任务状态 / 未被后续引用（典型：枚举式搜索迟迟不命中） | 连续冗余步段长度 |

但**信号只能"疑似定位"，不能直接定性**——同一个"连续多次调用"既可能是合理探索，也可能是低效重复。定性靠下一节的判别流程。

---

## 2. 四类区分的判别流程（方法核心）

把 RedundancyBench 的 `reason` 模式提炼成一套可操作的判据。核心思想是**分离两个视角**：

- **当时视角（prospective）**：在该步发生的时刻，agent 已知什么？这一步是否有合理依据？——决定它**该不该做**。
- **事后视角（retrospective）**：从完整轨迹回看，这一步的结果有没有进入有效路径？——决定它**有没有贡献**。

> **冗余 ≠ 不该做。** 冗余是"事后无贡献"，不该做是"当时无依据"。RedundancyBench 的 Exploratory 正是"当时有依据、事后无贡献"，这类最容易被误判。

判别决策树（对每个可疑步）：

```
这一步改变了任务状态 / 其结果被后续步骤或最终回复引用了吗？
├─ 是 → 非冗余（必要验证 / 必要操作 / 命中目标）
└─ 否（结果未被采用）
     │
     ├─ 它是一次外部/工具故障，且被后续成功重试取代？
     │     → Abnormal Step（错误恢复过程，有过程价值）
     │
     ├─ 它所需的信息/操作，更早的有效步已经提供过？
     │     → Duplicated Step（真正的低效重复）
     │
     ├─ 它发生时，目标/所需对象已经确定，此步没有合理依据？
     │     → Incorrect Step（真正的低效重复 / 不该做）
     │
     └─ 它发生时目标尚未确定，是缩小搜索空间的合理尝试？
           → Exploratory Step（合理探索，仅事后无贡献）★最易误判
```

**关键分界线**："命中前 vs 命中后"。目标未定位时的枚举/诊断 = 合理探索；目标已定位后仍继续枚举 = Incorrect。见 §4 的 R05↔R07。

## 4. 专题：看着没进展、实际上有价值（痛点核心）

当前最大的误判风险是把"有意义但失败的尝试"一刀切成低效。下面四个案例用统一框架论证它们**为何看着没进展却有价值**，以及**为何仍被标为冗余**（二者不矛盾）。

### 案例 A — 排除式枚举搜索（airline/27 R02）
用户只给航班号 HAT039、未给预订号。agent 从账户里**逐个核对 9 张预订**（GXWCPN→DQST39→…→HG8X9P）是否含该航班，直到 [24] 才命中 M61CQM。
- **当时视角**：目标预订未知，逐张核对是有合理依据的搜索，**每次"不含"都排除了一个候选、缩小了空间**——这是信息增益，不是空转。
- **事后视角**：这 9 张最终都不含 HAT039，没进入最终回复，故标 Exploratory。
- **价值**：排除法本身推动了定位；若没有这些"失败"查询，agent 无法确定 M61CQM 就是唯一含该航班的预订。
- **误判规避**：连续多次同类调用 ≠ 低效——先看发生时"目标是否已知"。

### 案例 B — 失败触发的错误恢复（airline/27 R03；telecom R11）
[8] 查 DQST39 遇 `Network timeout` 失败，[10] 立即原样重试成功；telecom [40] 遇 `Network error`、[42] 重试成功。
- **当时视角**：失败是外部故障，立即重试是**正确的恢复动作**。
- **事后视角**：失败那次无有效返回、被成功重试取代，故标 Abnormal。
- **价值**：失败步本身是"恢复过程"的一部分——它暴露了外部不稳定并触发了正确应对；评价应落在"恢复是否得当"，而非"失败=浪费"。

### 案例 C — 诊断性验证返回"无异常"也有信息价值（telecom R10 的 [22]）
支付前 [22] 查 B1234321 状态。即便返回"仍是待支付/无变化"，这一步也确认了"可以安全付款"。
- **当时视角**：执行不可逆操作（付款）前核对状态是必要验证。
- **事后视角**：[22] 未被标冗余（有验证价值）；而紧接着 [24][26] 连查两次完全相同才被标 Duplicated。
- **误判规避**：**验证步 / 探索步即使返回"无异常 / 无新信息"，首次仍有价值**；只有"同一验证在无状态变化下重复"才是低效。

### 案例 D — 命中前后的分界（airline/13 R05 ↔ R07）
同样是"枚举预订"，[6-15] 命中前标 Exploratory（合理探索），[16] 命中 XEWRD9 后，[18-25] 继续枚举却标 Incorrect（低效重复）。
- **这组对照是判别流程里最锋利的一刀**：动作相同、工具相同，仅因"目标是否已定位"而分野。
- **误判规避**：定性时必须带上"该步之前目标是否已确定"这一上下文，不能只看动作形态。

**小结——四条规避规则：**
1. 冗余（事后无贡献）≠ 不该做（当时无依据）；Exploratory 是前者不是后者。
2. 连续多次同类调用先问"目标是否已知"，再定探索 vs 低效。
3. 验证/探索步返回"无异常"**首次**仍有信息价值，只有无状态变化的重复才算低效。
4. 失败步按"恢复是否得当"评价，不按"失败=浪费"评价。

## 5. 两条完整轨迹的成本剖析（占位，待换真实 token 数据）

> 老师要求用两条"自己的完整轨迹"做成本剖析。因本人聊天记录尚未导出、本数据集无真实 token，**暂从 RedundancyBench 另选两条长轨迹占位**（不与 §3–4 的方法样例重复），全程用代理成本；后续可无缝替换为带 `usage` 的真实轨迹。

### 轨迹甲 — airline/18（48 msgs，21 次调用，无失败）
工具分布：`get_reservation_details ×6`、`search_direct_flight ×8`、`update_reservation_flights ×6`。冗余 9 步（Exploratory ×6、Incorrect ×2、Duplicated ×1）。
- **成本花在哪**：`search_direct_flight` 占调用近四成；最大单步返回在 [29]（≈740 token，一次航班搜索结果）。
- **值得进一步检查的阶段**：标注把 [16-43] 大段标为冗余，说明 agent 在"反复搜航班 + 反复改签"之间来回——**航班搜索与改签的往返**是成本黑洞，应检查是否在未锁定目标航班前就过早尝试 `update`。

### 轨迹乙 — telecom/104（104 msgs，30 次调用，1 次失败）
MMS 故障的长链诊断：网络→SIM→飞行模式→APN→重启→wifi calling→APP 权限逐项排查，`can_send_mms` 验证 3 次。tool 返回合计 ≈1379 token。冗余仅 5 步（Exploratory 1 / Incorrect 2 / Duplicated 2）。
- **成本花在哪**：成本主要在"调用次数"而非"返回体量"——30 次调用但单步返回都很短（设备状态类）。这是与轨迹甲相反的成本画像。
- **值得进一步检查的阶段**：开头 [8-19] 连查多条 line/bill 明细被标冗余（信息已在列表中），**诊断起步阶段的信息收集过度**是可优化点；而后半段的设备操作链（resume→reboot→toggle）几乎全有效，不必深查。

**两条轨迹的对照结论**：成本有两种截然不同的画像——**甲是"少调用、大返回"（上下文成本主导），乙是"多调用、小返回"（调用成本主导）**。识别冗余时，甲应盯"大返回的重复搜索"，乙应盯"起步阶段的过度信息收集"。这也印证：单一指标不足以定位成本，需调用数 + 返回体量两维合看。
