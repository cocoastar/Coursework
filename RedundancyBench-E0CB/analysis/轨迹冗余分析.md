# 轨迹冗余分析：哪些步骤看起来没用，其实值得做？

> 面向第一次接触 agent 轨迹的读者。本文使用仓库中的 RedundancyBench 人工标注数据；原始数据只读。文中的“条消息”与“一次工具调用”不是一回事，所有数字都说明了计算口径。

## 先用一分钟读懂这件事

**轨迹**就是助手完成任务时留下的全过程：用户说了什么、助手调用了什么工具、工具返回了什么、接下来又做了什么。比如用户只说“查一下 HAT039”，助手不知道是哪张订单，就要查订单 A、B、C……直到找到对应航班。

我们要找的不是“所有失败的步骤”，而是**花费了成本、但需要进一步判断是否值得的阶段**。例如：

- 查 A 不匹配，查 B 不匹配：**可能是合理探索**，因为目标仍未知，不匹配也帮助排除候选。
- 查订单时服务器超时，立即重试：**通常是合理恢复**；失败调用会花成本，但不等于助手做错了。
- 已找到目标订单，还继续查完全无关的其他订单：**值得怀疑**。
- 付款前查看状态，发现“待付款”：**可以是有价值的首次验证**；没发生变化也不等于没得到信息。
- 没有状态变化却连续三次查同一状态：后两次**很可能是低效重复**。

**一句话原则：不要凭“没得到最终答案”或“工具名字重复”就判低效；先问当时知道什么、这一步打算解决什么问题、结果改变了什么。**

### 新手词汇表

| 词 | 白话解释 |
| --- | --- |
| agent / 助手 | 会与用户对话并调用工具的软件助手。 |
| 消息下标 `[8-9]` | 第 8 条是发起工具调用，第 9 条通常是工具返回；从 0 开始计数。 |
| 区间 | 把一段连续消息合在一起研究，比如“找到目标前的搜索阶段”。 |

| 代理成本 | 没有真实 token / 耗时数据时，用调用数、返回字符数粗略描述体量；**不是账单**。 |

## 2. 数据与怎么算“成本”

原始位置：`../data/human_annotation/{airline,telecom}/final_traces.json` 存全过程，`annotation.json` 存已标出的冗余调用（`redundant_step_idx`、类别、证据等）；仓库 `../README.md` 和 `../data/human_annotation/README.md` 说明数据来源。本文使用**人工标注子集**，不把机器共识标签当成已经人工复核的结论。这个发布数据主要含“有冗余”的轨迹，不能推断一般助手任务的平均冗余率。

本报告的计算方式（例：[22-23] 为一次工具调用及其返回）：

- **调用数**：该区间内带 `tool_calls` 的消息里的调用个数；特别注明“助手发起”还是“用户侧发起”。
- **工具返回字符数**：该区间所有 `role=tool` 消息的 `content` 字符长度之和；这不包括全部提示词、思考文本、工具参数、用户发言、输出，也不等于 API 计费 token。
- **字符数÷4**：仅为便于目测大小的**粗略刻度**（中文、JSON、不同分词器的误差可能很大），以下用“约”表示。没有真实 token 与时间戳，就不能给出实际钱数、延迟或精确节省量。
- **有标签不等于浪费**：`Exploratory Step` 与 `Abnormal Step` 虽在标注集中被归为“事后冗余”，但前者当时可能是必要搜索，后者可能是正确的故障恢复；删掉它们不一定仍能完成任务。

原表选出的 12 条轨迹中，“被标冗余步骤占用的字符”与“全部工具返回字符”的比约为 **61.4%**（56703 / 92294；分子还包含少量助手文本，分母只含工具返回，所以严格说不是同口径占比）。这是**特意选取的冗余较多的 12 条**，不是所有样本的比例，更不是“可省 61.4% token”。原脚本对全部 189 条人工子集显示 31.3%，也有上述口径与选样限制。尤其不能将探索、故障、重复全部计为可删除成本。

## 3. 怎么找可疑阶段，又怎么避免误判？

**第一步：只提名“候选”，不要自动下结论。**

- 重复尝试：相同**工具名与参数**、针对同一对象，或反复获取同一内容。仅“工具名相同”不足以说明重复：连续查询不同订单就是反例；现有脚本 `n_repeat_calls` 实际统计“工具名重复出现的次数”，**不检查参数是否一致**。
- 失败与回退：先找工具报错以及下一次调用，再看是否重试成功；对于真正的“回退”，还要查有没有状态改回去（操作→检查→撤销→再操作）。**一次报错重试不是反复回退。**
- 长阶段没得到最终答案：观察连续调用是否没有完成最终任务，但同时记录是否缩小候选范围、确认条件或排除错误原因。这里的“长”主要指**调用次数多**；没有时间戳不能说“耗时长”。

**第二步：对每次调用问三个白话问题。**

1. 这一步之前目标找到了吗？是否已有相同信息？
2. 这一步之后获得了新证据（包括“这个候选不对”）、核实了风险，或改变了状态吗？若没获得，是不是外部系统故障？
3. 如果当时把这一步跳过，助手凭当时已有信息能安全做下一步吗？只问“事后答案会不会一样”不够。

| 判断 | 当时是否合理 | 事后是否进入最终有效路径 | 怎么写结论 |
| --- | --- | --- | --- |
| **合理探索**（Exploratory） | 是，目标未知且候选有依据 | 没直接用上 | “失败但有信息价值”；可研究更高效搜索方法，不直接判为坏。 |
| **必要验证 / 有效操作** | 是，需要确认付款状态或执行正确操作 | 有效路径的一环 | “没变”也可能确认了可继续；需结合操作风险判断。 |
| **错误恢复**（Abnormal） | 发生外部报错时，有限次数的正确重试有理由 | 失败结果被成功重试取代 | 记录失败成本，另评是否应重试、重试几次；不把故障归罪于助手。 |
| **真低效重复**（Duplicated） | 已有同样信息、期间无状态变化 | 没新增必要信息 | 优先复查相同对象、相同参数、相同返回。 |
| **无依据步骤**（Incorrect） | 目标已找到却继续查无关对象，或偏离请求 | 没贡献 | 优先复查动机；它和“调用完全重复”不是同一个概念。 |

注意：`Duplicated / Abnormal / Incorrect / Exploratory` 是数据集对**被标冗余步骤**的四种标签；“必要验证”是本文为**未被标注但确有依据**的步骤加的解释，不是数据集第五个标签。没有被标注，也不自动等于已证实必要。

### 两个最值得给老师讲的“看似没进展，实际有价值”例子

**例 1：airline/27，R02。** 用户只有航班号，不知道预订号。助手查了其他预订，8 次成功返回“不含目标航班”，一次超时没有排除任何候选，后续重试 DQST39 才得知不匹配。最终在 `[24-25]` 找到目标。从最终答案看，前面的预订都没被引用；从**当时**看，每次成功的不匹配都在排除一个可能对象。**结论：**这些查询“事后未直接贡献”与“当时有理由”可以同时成立；但仅凭这条轨迹不能证明这个查询顺序是最省调用的。

**例 2：telecom/overdue，R10。** `[10-11]` 时 B1234321 为 Overdue；用户收到付款请求后，`[22-23]` 的状态变成 Awaiting Payment，说明首次检查确实得到**新的状态证据**。`[24-27]` 没有发生新的变化，返回仍是 Awaiting Payment，因而后两次更有理由被判重复。**结论：**“看起来还没付款”并不等于“什么都没学到”。

**例 3：airline/27，R03。** 第一次查询得到超时而不是订单内容，立即重试得到了内容。失败调用是客观成本，但如果把整个恢复链判成“不该做”，就会误伤合理恢复。telecom/overdue 的 R11 更细：**恢复动作可理解，不代表成功重试返回的信息也一定必要**；先前若已拿到相同状态，仍应复查为什么又查了一遍。

## 5. 两条完整轨迹：成本究竟花在哪里？

下列两条来自数据集的**完整**轨迹（不是自己导出的聊天记录）。只分析可观察到的调用与工具返回；没有调用时间、真实 token 或 API 账单。用户侧工具调用也计入“轨迹调用”，但不能直接算作**助手的 API 工具费用**。

### 轨迹甲：airline/18，48 条消息

用户希望保留航班与乘客，将多张预订从商务舱改为经济舱。全程 **21 次助手调用、工具返回 18659 字符（÷4≈4665，仅粗略刻度）**；9 个工具步骤在原始标注中被列为冗余。

| 阶段 | 消息 | 次数及返回字符 | 花在哪，重点核查什么 |
| --- | --- | --- | --- |
| 定位账户与预订 | `[2-15]` | 7 次；5450 字符 | 先弄清涉及哪些预订；没有被标注的调用，不宜仅因量大就删掉。 |
| 最初搜航班及确认 | `[16-23]` | 3 次；2301 字符 | `[16-19]` 两次搜可用航班被标 Incorrect：用户要保留原航班，搜索是否偏题？`[22-23]` 标 Exploratory，应分开解释。 |
| 执行多张预订的降舱并穿插搜索 | `[24-45]` | 11 次；10908 字符 | 重点看 `[34-35]`：同一预订 X7BYG1 已在 `[32-33]` 更新，又做一次相同更新；另有多次被标探索性搜索，不要统称为反复“撤销/改签”。 |

工具类型分布：**搜航班 8 次 / 8559 字符**（约占返回字符 46%），更新预订 6 次 / 4650 字符，查预订详情 6 次 / 4472 字符，查用户 1 次 / 978 字符。一次较大的返回是 `[28-29]` 搜航班的 **2961 字符**；仅凭体量大不能判错，但它值得核查搜索目标是否必要。被标步骤共返回 **9322 字符**，其中包含合理探索，不能把它全算作可节省额。

### 轨迹乙：telecom/MMS（104 条消息）

用户遇到 MMS 无法发送，过程涉及账户核查、数据服务、飞行模式、SIM、APN、Wi-Fi Calling、应用权限，最后三次测试用于定位与确认修复。全程 **30 次工具调用=助手 10 次+用户侧 20 次**；工具返回 **5517 字符（÷4≈1379）**。这是**调用次数多、返回总量相对小**的案例，不是“30 次助手 API 工具调用”。

| 阶段 | 消息 | 次数及返回字符 | 花在哪，重点核查什么 |
| --- | --- | --- | --- |
| 起步诊断、账户及账单 | `[3-28]` | 11 次（助手 10、用户侧 1）；3883 字符 | **全部 5 个被标步骤都在此段**。`[14-15]` 账单列表一次返回 1572 字符；`[26-27]` 再次补同样 2GB，原始标注为 Duplicated，需重点核查有无重复收费/副作用。 |
| 检查网络、SIM、APN 等 | `[29-72]` | 11 次（用户侧）；1126 字符 | 操作改变设备状态，APN 重置后重启、再查 APN；“又查一次”发生在状态变化**后**，并非必然重复。 |
| MMS、Wi-Fi Calling 与权限排查收尾 | `[73-103]` | 8 次（用户侧）；508 字符 | `can_send_mms` 有 3 次，分别夹在修复动作前后；最后由“不能发送”变为“能发送”。应按状态变化解释，而非见到同名工具三次就打重复标签。 |

这条轨迹的被标步骤返回字符总计 **2486**，不是可以直接省掉的 2486 字符；报告应优先关注**起步过度取数**和**潜在重复修改状态**，不要把后面的修复链叫“没进展”。

### 合在一起看

甲的主要**工具返回体量**来自航班搜索；乙的主要**调用次数**有很大一部分来自用户操作。比较“成本”至少分开记三项：①助手工具调用次数；②用户侧操作次数；③每段工具返回体量。若有真实 `usage` 和时间戳，再补充输入/输出 token、API 账单、单次与累计耗时，才可以讨论“到底省多少钱/多久”。

## 6. 接下来怎么完善，才更像高质量调研？

1. **补三篇文献**：在本文加一个“三篇各研究什么 → 各自如何看待失败尝试 → 我的案例支持/修正哪里”的对照表；没有文献原文前不编造引用。
2. **真实成本**：选两条有 `usage`、工具开始/结束时间和模型计费的数据；分别算助手调用、用户动作、输入/输出 token 与墙钟时间。没有日志时维持代理成本，不外推为实际费用。
3. **定义“可删除”的反事实**：对每个“重复”追问“去掉它后，能否按当时可见的信息安全完成任务？”对探索/报错单列“必要但失败/成本可能优化”，避免把标签当节省率。
4. **补真正回退样例**：找确实发生“操作→撤销→再操作”的轨迹，记录状态前后变化；当前 R03/R11 只能证明一次故障与重试，不能证明“反复回退”。
5. **复核争议项**：例如首次验证是否必要、同名不同参数是否合理、支付/补流量是否有副作用。每个区间记录“当时已知→本步结果→后续使用→可替代方案→仍存疑问”。

### 如何复现与继续读
